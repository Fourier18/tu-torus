## Vision

A live-tu-torus app. Three panels. Any language, no setup step, no language menu. **[R20]** No built-in model or subscription — the tutor connects to whichever provider you pick in Settings, Mistral/Codestral by default. Built to scale beyond personal use.

## Panel 1 — Editor

- Monaco or CodeMirror, embedded, with named files/tabs.
- **[R2] Language comes from the file name** (`main.py`, `index.html`, `hello.rs`), the way every editor already works. No dropdown, no model call. (Rev 1 said Claude would detect the language on every Run — that would have added seconds of delay and a tutor call to every Run, breaking the "tutor only acts when asked" rule.)
- Autosaves ~2 seconds after typing stops. **[R3] The tutor reads your current code from disk when a question needs it, so autosave is what keeps the tutor current.** (Reverses R2's "the tutor doesn't need it.")

## Panel 2 — Output canvas

**[R6] The output panel behaves like a browser, not a tool with settings.** A browser never asks you to turn on a "render HTML" mode — it just shows you what the content is. This panel works the same way: there is no mode, no toggle, nothing the user or the tutor ever selects. Never describe this as having "modes" again — say what it does (shows content the way a browser would), not how many branches the code has internally.

What that means concretely, with no user-visible seam between the two:

- A file a browser can open directly (HTML, SVG, an image, plain text) is shown directly, the same as double-clicking it would.
- A file that needs a language runtime to produce anything runs on whichever engine `languages.json` configures for it, and its output — text, almost always — is shown as that.

The extension-to-runner mapping is a config table (extension → how to run it), never a hardcoded if/else, so adding a language is adding a row, not a code change.

**[R18] Execution engine, corrected — no Docker, no Piston.** Earlier revisions (5, 7, 10) built this on self-hosted Piston, which needs Docker. That was solving the wrong problem: Piston/Judge0-style sandboxing exists to defend a *shared server* from *strangers'* code. This app has neither — it's one person running their own code on their own machine, the same as opening a terminal themselves. There's no attacker in that model, so container-grade isolation was never actually required; what matters is ordinary hygiene. Current engines, dispatched per extension:
  - **Pyodide, in a worker thread** (`server/src/engines/python.js` + `python-worker.js`) for Python. Runs in-process, bundled with the app — no install, no daemon. Real interactive `input()` works via a `SharedArrayBuffer` + `Atomics.wait`/`notify` bridge between the worker (which genuinely blocks) and the main thread (which holds the live WebSocket) — this is the standard pattern for blocking stdin in a worker/WASM setup, confirmed with a timestamped test proving the block is real, not pre-buffered.
  - **A local toolchain, run as a plain subprocess** (`server/src/engines/toolchain.js`) for everything else — whatever compiler/interpreter is already on the machine (`node`, `rustc`, `go`, `gcc`, `ruby`, `php`, etc.), detected via `where`/`which`. Hygiene, not isolation: a 15s hard timeout, the whole process tree killed on timeout (not just the parent), output capped, and a fresh throwaway temp directory per run. If a language's toolchain isn't installed, that's said plainly (`"<command> isn't installed... install it to run .<ext> files"`) rather than failing silently or hanging.
  - Confirmed working, for real, not assumed: Python, JavaScript (via `node`), and Rust (compile-then-run via `rustc`, proving the two-stage path). Go correctly shows the "not installed" message rather than crashing. C#, and several others in the table, are configured but not yet verified against an installed toolchain on this machine — say so if asked, don't claim they're tested.

Input:

- **[R2] An input line is present whenever a program is running** and takes focus when output goes quiet; it disappears when the program ends. Neither engine above signals "now waiting for input" distinctly from other output, so this stays the right design.

Errors:

- **[R2] If the program crashes, the canvas shows one plain line** ("Program stopped with an error"). The full error text goes into the run record for the tutor. (Rev 1 showed stdout only, so a crash would have left a blank panel.)

**[R2] Known limits (not being built now):** programs that open desktop windows (Python turtle, pygame, matplotlib pop-ups) won't display; Pyodide's Python has no internet access and only the standard library unless a package is explicitly loaded.

## Panel 3 — Tutor chat

- **[R20] No subscription/OAuth login — a real provider choice instead.** Anthropic's terms don't allow third-party apps offering claude.ai login, and this repo is public, so the Claude Agent SDK path (R18's `claude.js`, sign-in at setup) is gone entirely. One generic OpenAI-compatible chat-completions client (`server/src/providers/openai-compatible.js`) is now the only provider — Settings picks a preset (Mistral/Codestral default, Gemini Flash, OpenRouter for everything else, or Custom for any other OpenAI-compatible endpoint, local or cloud) that fills in a suggested base URL and model, every field staying user-editable. An API key is saved only in `.tutor/settings.json` on the user's own machine — never committed, never logged.
- **[R20] No agentic tool-use loop anymore.** The Claude-only Read/Glob/Grep tool access (R3's "three read-only tools") doesn't carry over to an arbitrary third-party model — nothing here can be trusted to honor the same restrictions at the tool level. Instead, everything the tutor could need is assembled server-side and handed over in the message itself: current code, the last run's full record (output + error), and a trimmed slice of recent chat history. A disclosed tradeoff, not a hidden gap — the same principle R18 already established for the old `custom.js` path, now just the only path there is.
- **Strictly reactive.** Never edits the code. **[R20] "Reactive" now means four explicit triggers, not "only on user submit":** a typing pause of a few seconds, a run that just finished with an error, the "Check my code" button, or a typed question. Never fires per keystroke, never on a timer unrelated to one of those four.
- **[R20] Trimmed history, not full-session or stateless.** Earlier revisions alternated between "no memory, re-read files every call" (R3, needed the agentic loop) and would otherwise have meant "resend everything forever." Now: the last few turns (`HISTORY_KEEP = 6` in `TutorChat.jsx`) are sent as real `user`/`assistant` messages alongside the new turn, giving short continuity without an unbounded, ever-growing context.
- **[R3] Every Run still writes a run record** (run number, file name, code as run, output, full error) and it's still attached once, to the next tutor call, not to every message.
- **[R20] Rate-limit and auth errors surface as real messages in the chat panel**, never a silent failure: 429 → "Rate limit reached — try again in a minute" (no specific number, since every provider here changes its free-tier limits over time); 401/403, or a response body that reads like an auth failure even under a different status code (confirmed necessary: Gemini's OpenAI-compat layer returns a plain 400 for a bad key) → "Invalid API key for `<provider>`."
- Considered and cut this pass: attaching a screenshot of the rendered output canvas to a tutor message. Blocked on a real constraint found by testing, not skipped for time — see Revision 20 below.

## Usage / context handling

**[R20] Estimate**, current architecture (a ~30-message session, ~100-line script, half the messages come after a new Run):

Per message: system prompt (~120 tokens, fixed text, cacheable on providers that support prompt caching) + current code (~150–400 tokens for a beginner script) + last run's record when one exists (~200–800 tokens, attached once per new run, same as R3) + up to 6 trimmed history turns (~50–150 tokens each). No SDK-level prompt caching or compaction here (that was Agent-SDK-specific) — the trim cap is what keeps this bounded instead.

Rules:

1. **[R3] Run record cap keeps the first and last part of the output**, never cuts the error, and saves the full output to the run file. (Read once per call from disk, not resent from the frontend.)
2. **[R3] Keep the last 20 run files**, delete older ones.
3. **[R20] History is capped client-side** (`HISTORY_KEEP`), not left to grow with the session — no SDK-level compaction to lean on anymore.
4. **[R20] Default preset (Mistral/Codestral) and every other preset are changeable in Settings**, same as R3 intended for its model picker.
5. **[R20] Per-message usage logging is gone** — most OpenAI-compatible providers don't report token usage on a streamed response, so R3's "log usage from day one" (built for the Agent SDK, which did report it) has nothing left to log; not rebuilt as a fake/estimated number.

Not adopted: sub-agents (one tutor, nothing to split); a per-model image-input capability table (a model that can't take an image will just error clearly, same as any other rejected request — not worth the maintenance cost of tracking it).

## Stack

- Frontend: React — editor, output canvas (text mode + sandboxed iframe mode), chat.
- Backend: a thin server holding the run-engine dispatcher (Pyodide + local toolchains, `server/src/runner.js`) and the tutor's context assembly (`server/src/tutor.js`, calling the one provider in `server/src/providers/openai-compatible.js`).
- Packaging: Electron (`electron/main.js`), built as a real Windows installer via `npm run package` — no Docker, no separate Node.js install required to run it.

Revision 18 (2026-09-24): the full Docker/Piston removal and Electron packaging pass — the single biggest architecture change since the original design. Summary, with the real bugs found along the way (each one found by actually testing, not assumed):

- **Execution engine replaced.** Piston/Docker are gone entirely. Python runs on Pyodide in a worker thread (`server/src/engines/python.js` + `python-worker.js`) with real blocking interactive `input()` via `SharedArrayBuffer`/`Atomics` — proven with a timestamped test, not just claimed. Everything else runs via an installed local toolchain as a plain subprocess (`server/src/engines/toolchain.js`) — hygiene (timeout, process-tree kill, output cap, throwaway temp directory), not container isolation, because this app's real threat model is one person running their own code on their own machine, not a shared server defending against strangers.
- **Two real bugs found in the Python engine itself, both by testing:** (1) Pyodide's `batched` stdout only flushes on a newline, so `input()`'s prompt (no newline) sat unflushed — switched to `raw`. (2) The `raw` fix was then defeated by `Atomics.wait()` blocking the worker's whole event loop, microtask queue included, so a *deferred* flush never actually sent until after the block ended — fixed by posting immediately, no deferral. Also fixed: per-byte decoding was mangling multi-byte UTF-8; switched to `TextDecoder`'s streaming mode.
- **Provider abstraction actually built, not just described.** `server/src/providers/claude.js` (default) and `custom.js` (a generic OpenAI-compatible adapter — covers most local servers and most cloud providers with one implementation) both yield the same normalized shape; `tutor.js` routes between them. Onboarding lives in Settings, not a config file.
- **Packaged as a real Electron app**, not a `.bat` file — a genuine installer, a real window (no browser chrome, correct taskbar title — the default Vite scaffold title ("frontend") was still showing in the title bar until caught and fixed, with the window title also locked against being overridden by the page's own `<title>` tag going forward).
- **The packaged app's Claude tutor connection failed for a real, subtle reason, found only after extensive isolated reproduction:** the Agent SDK spawns its bundled `claude.exe` using the same `cwd` the app configures for the tutor's own file access — but `workspace/` was never included in what gets packaged, so in the installed app that directory didn't exist at all. Windows' `CreateProcess` can fail with `ENOENT` for a *missing working directory*, not just a missing executable, which is exactly why the SDK's own error message ("binary exists but failed to launch") was misleading — the binary was always fine. Fixed at the source in `paths.js`, which now creates the directory itself rather than depending on a packaging `files` glob staying in sync. Several other plausible causes were tested and ruled out along the way (asar packing needing `asarUnpack`, `ELECTRON_RUN_AS_NODE` leaking into the grandchild process, portable-mode's fresh-extraction-per-launch) before this was isolated — none of those were the actual cause, but each was verified rather than assumed.
- **One more real bug, caught by the tutor itself during verification:** `python.js`'s rewrite (done under time pressure during the Docker removal) dropped output accumulation entirely — the browser's live stream still worked (a separate code path), but every run record was being written as "(no output)" regardless of what the program actually printed. Found when the tutor, asked what a run printed, correctly reported the record said nothing — which was true of the record, not of the actual run. Fixed and reverified with both a success case and an error/traceback case.

Every item above was verified against the actual packaged, installed `.exe` — not dev mode, not assumed from the source — before being called done.

Revision 20 (2026-09-25): Claude subscription/OAuth removed entirely, replaced with a provider-agnostic tutor and real trigger logic. Summary, with what was actually tested, not assumed:

- **Provider layer rebuilt.** `server/src/providers/claude.js` and the old `custom.js` are both gone; `server/src/providers/openai-compatible.js` is the only provider now, and `tutor.js` no longer routes between two — it just assembles context and calls it. Settings (`Settings.jsx`) gained a provider dropdown (Mistral/Gemini/OpenRouter/Custom), with base URL, model, and API key all staying user-editable after a preset fills them in.
- **Every preset's base URL and default model was checked against that provider's current docs, not assumed from training data** (confirmed necessary — Mistral's Codestral is reachable through the standard `api.mistral.ai/v1` endpoint with a normal key, not the separate `codestral.mistral.ai` endpoint some docs imply; Gemini's `gemini-flash-latest` alias was chosen specifically because Google has shipped four Flash models in about 100 days this year, and a pinned dated model would have gone stale fast; OpenRouter defaults to `openrouter/free`, a real router that auto-picks from currently-available free models — checked directly, since a pinned single free model was confirmed unstable: the actual current free-models collection didn't contain the model an initial search suggested pinning).
- **Real bug found and fixed by testing, not by inspection:** the first version only sent the tutor a pointer saying a run existed, never the code itself — so even a basic "what's wrong with my code" question cost a full extra round trip. Fixed by inlining the current file directly into the message. Measured before/after: this alone didn't fix the reported ~15s lag (traced separately to the Agent SDK never streaming partial output — see the session's own record for that fix, made just before this revision), but it removed a real, unnecessary round trip that would have mattered on the new architecture, where there's no tool-use loop left to fetch it another way.
- **Trigger logic replaced.** `TutorChat.jsx` previously fired only on manual submit. Now fires on a typing pause (`PAUSE_MS`, skipped if the code hasn't actually changed since the last check), a run that finished with `ok: false` (tracked end-to-end: `run-records.js` now returns `ok` alongside the pointer, relayed through the WebSocket `run-recorded` message, not re-derived by string-matching the pointer text), the "Check my code" button, or a typed question. Auto-fired turns show a small system-styled note (`chat-system`) instead of a fake user bubble, so it's visually clear the tutor spoke unprompted.
- **Rate-limit and auth errors handled explicitly**, confirmed against the real endpoints, not assumed: a 429 shows "Rate limit reached — try again in a minute" (no specific number — free-tier limits shift over time on every provider here). A 401/403 shows "Invalid API key for `<provider>`." Status code alone isn't reliable across providers — confirmed directly by testing a bad key against Gemini's real endpoint, which returns a plain 400 (`INVALID_ARGUMENT`) instead, with the real reason only in the body text; the provider now also checks the response body for auth-shaped language as a fallback, and this was verified to correctly catch Gemini's case without breaking the other two.
- **Considered and cut: attaching a screenshot of the output canvas to a tutor message.** Built once with `html2canvas`, then found by direct testing that the output iframe's `contentDocument` is `null` from the parent — a direct consequence of `sandbox="allow-scripts"` with no `allow-same-origin`, which is exactly what keeps a learner's rendered HTML/JS from reaching the parent app and is not something to weaken for this. The correct fix is Electron's `webContents.capturePage()` over a real IPC bridge (a preload script, `contextBridge`, `ipcMain.handle`), which doesn't exist yet and couldn't be verified in this session without a full package-and-reinstall cycle that would have interrupted the app already running on this machine. Cut rather than shipped as a button that would have silently done nothing; `html2canvas` was removed again after confirming `npm uninstall` left `frontend/package.json` and its lockfile byte-identical to before.
- **Every change in this revision was tested against the running code, not just written and assumed correct:** the provider's own error paths (429/401/403/unreachable-host/Gemini's 400 case) were each hit for real against the live Mistral, Gemini, OpenRouter, and an intentionally-unreachable localhost endpoint; all four chat triggers (pause, run error, check button, manual question) were exercised in the real browser via a real edit → pause → run-to-failure sequence, not simulated; the frontend build was run clean before calling this done.
- Left alone deliberately: the app's own currently-*installed* build still has the old Claude/OAuth code baked in and keeps working as-is — this revision only changes the source going forward, nothing was rebuilt or reinstalled as part of it.
