### Classic BASIC shortcuts and dialects (user request, 2026-09-27; not built)
- **Trigger:** `10 ? "hi"` in a .bas file gave "invalid syntax at line 1 col 4". The bundled interpreter (qbjc) follows QBasic/QuickBASIC grammar, which has no `?`. (QBasic's own editor accepted `?` by turning it into PRINT as you typed; qbjc has no editor, so it never sees that step.) The user wants the 1980s shortcuts for nostalgia.
- **Step 1, small:** translate shortcuts before the program reaches qbjc. `?` at the start of a statement (after a line number or `:`) and outside quotes becomes `PRINT`. This is how QBasic itself treated `?`. Error line and column numbers must stay right.
- **Step 2, bigger:** a real Commodore 64 BASIC V2 mode (and optionally Applesoft), the C64's own dialect: `?`, keyword abbreviations (the C64 typed e.g. `pO` for POKE), line-numbered-only programs, `GOTO`/`GOSUB`, PEEK/POKE on emulated memory, variable names significant to two letters, the 40-column screen feel. Options: a small interpreter written for this (BASIC V2 is small; open-source JS versions exist to evaluate), or an emulator running the real C64 BASIC. The real ROM is copyrighted, so an emulator needs a clean-room BASIC or a license. Pick the dialect by file ending (e.g. `.c64`, `.bas` staying QBasic) or by a first-line marker.
- The tutor should know which dialect a file runs as. It correctly said `?` is old-microcomputer syntax this interpreter doesn't take.

### Skins — designed-object looks for the whole app (user idea, 2026-09-27; not built)
- **What it is:** a skin redesigns what each part *is* as an object (shape, frame, texture, decoration) around one aesthetic, where a theme only recolors. The layout and every control's place and job stay fixed: editor left, output middle, tutor right, Run bottom-right of the output panel, Settings top-right.
- **Examples (user's):** *Fantasy / D&D*: each panel an unrolled parchment scroll (rolled ends, aged-paper texture); buttons as set gems (Run a large cut gem); carved-wood or leather-and-metal frame. *Cyberpunk*: circuit-board backgrounds, neon glow on edges and trim, panels as hard-shell hardware casings (angular corners, bolted plates, status lights), buttons as lit keys/switches.
- **Depth:** a blurred, out-of-focus background layer (fuzzed circuitry, a blurry city skyline) behind sharp, in-focus foreground pieces, for a 3D feel.
- **Must feel like real designed objects**, not a picture dropped behind the current layout, so each skin needs its own art for its pieces (scroll ends, gems, casings), as SVG or images.
- **Readability rule:** the working areas stay readable and behave the same (code, program output, tutor replies, typed input). Decoration frames them and never covers them. Contrast is measured per skin, as was done for the themes.
- **Themes vs skins:** themes apply only to the plain, unskinned app. A skin brings its own colors, so while a skin is on, the Theme choice doesn't apply (hide it or grey it out and say why). Choosing "no skin" returns to the chosen theme.
- **Build notes:** mostly a styling swap, as the user expects: skins as separate style files keyed off a `data-skin` attribute, like `data-theme` today. Two things aren't pure CSS: (1) the art itself has to be made per skin; (2) some pieces need hooks in the page (extra elements or class names for scroll ends, gem sockets, panel casings), and the inline styles in Settings.jsx need moving to classes so a skin can reach them. The editor (Monaco) needs its own matching color theme per skin, like the themes have now. Blur layers cost some drawing performance; check on a modest machine.

## Decisions — scope and direction

### Scope decisions — out of scope for this product (user, 2026-09-26)
- **Not a demonstrator.** The tutor never writes and runs its own example programs. It explains, and may show code as text (inline backticks or fenced blocks). Its private `run_learner_code` runs exist only to check the learner's *own* code before making claims about it.
- **Not a course / LMS.** Tu-Torus is user-directed: it responds to what the learner is doing, it doesn't lead them through a curriculum. An exercise generator or guided lesson path would be a separate product — don't propose it as a Tu-Torus feature.

### Learner notes — research on the remaining imperfections (2026-09-26, proposed, not built)
Problems: (a) notes churn mid-session; (b) progress gets lost — returningLearnerHard removed the stale "new to coding" but never recorded "not new anymore, writes classes", ending with nothing.
- **Update, don't delete** — Mem0 classifies each change as ADD / UPDATE / DELETE / NOOP, and UPDATE replaces a memory with a richer version ([Mem0 paper](https://arxiv.org/html/2504.19413v1)); a known Mem0 failure is silently deleting a memory still needed ([DEV](https://dev.to/mukesh_13/mem0-auto-resolves-memory-conflicts-for-you-until-it-silently-deletes-one-you-still-need-4f4m)). Zep/Graphiti invalidate superseded facts instead of deleting them ([Zep paper](https://arxiv.org/abs/2501.13956)). → Replace our `remove` with `update` (old line → corrected line); a bare delete only when the learner asks; keep superseded lines in a history file so a wrong change can be undone. Fixes (b).
- **Stability / hysteresis** — overwriting a stable profile fact should need repeated evidence, not one sentence ([CAPTURE](https://arxiv.org/pdf/2609.02265)); SSGM separates memory evolution from use and adds consistency checks and decay ([SSGM](https://arxiv.org/html/2603.11768v1)). → Two tiers: a stable "About them" section (self-statements, long-running patterns) that changes only on an explicit self-statement or a repeat across exchanges/sessions, and a volatile "Working on now" section that may churn freely and is cleared or folded in at the next session start. Fixes (a) where it matters.
- **Batch, don't write every turn** — session-end or idle-time consolidation instead of per-turn writes ([Wire](https://usewire.io/blog/when-agent-memory-needs-sleep/), [consolidation survey](https://arxiv.org/html/2603.07670v1)); a tutor project gating/batching extraction for the same cost reason ([dana-ai #33](https://github.com/Amirmfth/dana-ai/issues/33)). → Per-turn step only proposes grounded candidates; one consolidation merges them at the next session start (the server can't reliably call the model while the app is closing). Also cuts requests per reply.
- **Positive evidence, verified** — learner models should track what learners can do, not just errors ([Frontiers 2026](https://www.frontiersin.org/journals/education/articles/10.3389/feduc.2026.1896839/full)). Our ban on code-based evidence stopped over-crediting but also blocks real progress. → Narrow, checkable exception: a code line the learner wrote that fixes the problem and does not appear in any earlier tutor reply counts as evidence ("fixed the loop bound before being told").
- **Open learner model** — letting learners see and discuss/edit their model supports reflection and improves accuracy; one study found students trusted it more when they couldn't change the assessment ([Bull & Kay, Open Learner Models](https://link.springer.com/chapter/10.1007/978-3-642-14363-2_15), [negotiation approach](https://link.springer.com/chapter/10.1007/978-3-031-98281-1_12)). → Keep editing; add pin/lock for lines the learner confirms, and a small "notes updated" indicator with history.
- **Measure first** — build a notes eval with ground-truth facts per simulated persona: churn per session, final-note accuracy, retention across sessions, over-credit count (must stay 0).

## Open Challenges

- **Instruction-following ceiling on free-tier/weaker models is the central unresolved risk.** Two structural rules have now been written into `tutor-instructions.md` (repetition/ground-truth, then one-thing-per-response) specifically because a live test violated them despite being explicitly stated. Prompt engineering can reduce how often this happens but there's no guarantee any given free-tier model reliably obeys either rule — this app has no automated way to catch a violation when it happens, only manual spot-checking. Worth watching whether the second fix (below) actually holds up under more testing, or whether this is a real ceiling that no amount of rewording gets past for weaker models.
- **No persistent learner-level model.** Each tutor call is stateless beyond `HISTORY_KEEP=6` trimmed turns — the tutor can't track "this learner already understands loops but struggles with recursion" across a session, let alone across sessions. Flagged in the SocratiCode-based rewrite as a known gap, not fixed.
- **Provider model catalogs still require the user to look something up.** The blank-model-name fix (below) solves staleness but trades it for friction — a brand new user has to leave the app once to find a model ID before the tutor works at all. No better tradeoff found yet.
